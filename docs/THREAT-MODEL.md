# Varlatch Threat Model

Consolidated from Varlatch's design decisions and readable on its own. Honesty is the design
principle: every strong claim below either maps to an automated test, an
integration/E2E check, or a deployment invariant, or it explicitly states why
the property cannot be enforced.

## In plain English (TL;DR)

- **What is protected:** Every stored value is envelope-encrypted inside
  `varlatchd` (`Root KEK → Organization KEK → per-version DEK`). A stolen
  database or backup alone reveals no plaintext values. Authorization is
  default-deny, every disclosure is audited before decryption, and human logins
  are passkey-only.
- **What is protected with AI agents:** In `--agent-safe` mode, an AI agent
  holds opaque Placeholders instead of Secrets, and a local Broker injects real
  values only into HTTPS requests to allowlisted hosts and declared locations.
  In `--assisted` mode, the CLI guards against accidental leaks (output masking,
  explicit confirmations) when an agent acts with your own credential.
- **Who is trusted:** Anyone with `root` on the server host, access to the
  `varlatchd` process/container, or access to the Root KEK is an
  **Infrastructure Operator**—above application-level policy. Varlatch audits
  host interventions rather than pretending to block root.
- **What is NOT claimed:** Plain `varlatch run` hands plaintext to the child
  process (so the app can use it). Output redaction, secret scanning, and
  assisted mode guard against accidents, not a malicious process running as your
  own OS user. Root KEK rotation in place is not yet shipped.

Claims below carry one of three statuses:

- **SHIPPED GUARANTEE**: implemented and verified by tests/E2E/deployment invariants.
- **DESIGNED INVARIANT**: an architectural rule the implementation follows and enforces where it applies today.
- **DESIGNED / NOT SHIPPED, NOT CURRENTLY GUARANTEED**: planned architecture; no protection exists yet.

## 1. Assets

Plaintext configuration Values and Secrets; the Root KEK; Organization KEKs
and per-version DEKs; Varlatch credentials (service/CLI/browser bearers,
setup/invite grants, browser sessions and passkeys); authorization state
(identities, memberships, Grants, Requirements, Contracts);
the Security Audit history; the Backup Encryption Key; the tailnet node's
identity and the public certificate's key.

## 2. Principals and trust zones

| Zone | Members | Trust |
|---|---|---|
| **Infrastructure Operator** | Anyone with root or exec on the host or in the container, the data directory, the running binary or image, or the KEK (includes Coolify terminal access and whoever can deploy the image) | **Above the application's enforcement.** Varlatch makes operator actions explicit and audited; it never claims to prevent them. |
| **Secret Plane** (`varlatchd`) | The daemon, its SQLite database, the KEK in memory | Trusted. Its compromise may expose all secrets. |
| **Application Plane** (the dashboard's code in a browser, and its live-update stream) | The dashboard's files, which `varlatchd` embeds and serves; change signals | Untrusted for authority: can break UI, never authorization. It acts only as the signed-in person, through `/v1`. |
| **Authenticated Identities** | Humans (installation-level), machine identities (org-scoped) | Only what Grants + roles allow, per request. |
| **Network peers** | Public internet, tailnet peers | Nothing by presence. Tailnet identity is an *additional* constraint or an explicitly enrolled authentication method, never ambient authority. |
| **AI agents / untrusted subprocesses** | Anything `varlatch run` spawns | Untrusted. In agent-safe mode (§6) an Agent Run holds only placeholders and no Varlatch credential; plain `varlatch run` still injects plaintext (§5). |
| **Local Broker** | The loopback proxy `varlatch run --agent-safe` starts in the trusted parent | Trusted for mediation only: it holds the broker credential and sees plaintext at the substitution boundary, but `secret.use` authority belongs to the Agent Identity and is evaluated by `varlatchd` per exercise. |

## 3. Trust boundaries

1. **Application Plane ↔ Secret Plane.** The dashboard is static files: it holds no key material and no authorization state, and reads everything from `/v1` with the signed-in person's bearer. The live-update stream carries signals only (which Organization changed, in which domains, when, and the last audit event's ID), never data. One process serves both, so this boundary separates authority, not memory: compromise of `varlatchd` is compromise of the Secret Plane.
2. **One process, one database file.** `varlatchd` alone writes the SQLite database, through a single writer. There are no database roles: the rules the database itself holds (append-only audit, gapless audit positions, forward-only passkey counters, a session's end revoking its credentials) are triggers in the same file, which bind every statement `varlatchd` runs but not someone who can open the file. The file is the service user's alone (a data directory of mode 0700), and one running owner holds its lock. On systemd the service runs as its own user with `NoNewPrivileges`, a read-only file system but for its state directory, and no core dumps; the container image runs as uid 65532 and needs no capability and no writable path but its volume.
3. **Bearer-only `/v1`.** Cookies authenticate only the `/auth` ceremony surface; the browser exchanges its httpOnly session for a short-lived in-memory bearer, which ends with that session.
4. **Ordinary listener vs tailnet listener.** Trusted Tailnet Context can only be constructed on the dedicated tailnet listener from the true socket peer via WhoIs; headers, forwarded IPs, and CGNAT-range sources never create it. The tailnet listener is never reverse-proxied. Its optional browser endpoint (HTTPS, off by default) terminates TLS inside varlatchd with the node's own certificate, so the same socket peer reaches WhoIs, and never resumes a TLS session, so every connection is checked for the name and a valid certificate; it answers only the node's name, lets only exactly allowlisted origins read cross-origin, and only on the value-read routes, and cookies never authenticate there.
5. **Human authentication.** The passkey ceremonies and browser sessions answer "who is this human?" and nothing else: a session is an Identity's, confers no Grant, and only exchanges for that Identity's short-lived bearer.

## 4. Shipped guarantees

Each maps to its verification, in three forms:

- **A Go test**, named by its package under `go/`: `server/values.TestStrictRetrievalFromItsSnapshot`. All run in CI.
- **A replay**: the last TypeScript server's recorded answers to a table of requests, about 2,400 in all, replayed against `varlatchd`, which must give the same status, body, audit events and changed rows. *replay `access`* is `go/server/paritytest/testdata/access-v0.22.0.json` (`values`: `go/server/values/testdata`), run by a Go test of the package that serves it. Where the Go server differs on purpose, the test says so.
- **A suite** of the conformance harness (`scripts/conformance`), end to end against a running `varlatchd`, in a browser where the claim is the dashboard's: *suite `broker`*.

A claim that rests on fewer cases than the TypeScript server's tests had says
so. `scripts/conformance/test/threat-model.test.mjs` fails when a test, a
replay or a suite named here does not exist.

## 5. Explicit assumptions and non-guarantees

These are the boundaries of the model. None of them is a bug.

- **The Infrastructure Operator is outside enforcement.** Root, exec, data-directory, binary or KEK access defeats everything, including audit: the database's own rules are triggers in its file, which hold against what `varlatchd` runs, **not** against an operator who can open the file elsewhere, restore old state, or replace the binary. Operator-resistant audit evidence would require an external trust anchor and does not exist yet.
- **`varlatchd` compromise may expose all plaintext** the process can decrypt, plus the KEK in memory. The Secret Plane is the trusted computing base.
- **KEK loss is permanent data loss.** An archive, its backup key and the matching Root KEK are recoverable together; none alone is. The *raw* keys stored with the backup weaken theft protection to nothing. `admin kek export` produces a passphrase-wrapped escrow blob (scrypt + AES-256-GCM, KDF parameters AAD-bound) that IS safe to store with backups; loss then reduces to passphrase loss. `admin kek split`/`combine` provide k-of-n Shamir sharing for multi-custodian setups; fewer than k shares reveal nothing. Both recovery paths verify against the installation canary before writing a key file when the database can be read; on a fresh host, before the database is restored, they warn that the key was not checked and write it, and `admin kek verify` checks it afterwards.
- **Organization isolation is tenant isolation, not protection from the operator** of the installation.
- **Installation Admins have a real escalation path**: recovery mediation can take over any human identity, including Organization Admins. It is allowed, single-admin, and loud (high-severity audit), not prevented.
- **Code running in an allowlisted page on an approved device can read what that device may read.** With the tailnet browser endpoint, the device check binds to the device, not to the page: once a person has connected in a tab, a script injected into the dashboard can use its bearer against the endpoint exactly as the dashboard does. The dashboard's strict Content-Security-Policy (scripts and styles from its own origin only, nothing inline, connections only to its own origin and the endpoint) makes injection harder; it does not make injected code safe. The CLI on that device has the same exposure; audit names the device and the client.
- **Tailscale limitations**: revocation is bounded by local netmap freshness (a removed node may retain access until the netmap syncs); tag enrollment delegates identity issuance to whoever assigns that tag in the tailnet; a compromised machine that legitimately satisfies identity and policy can exercise whatever that machine is allowed. Tailnet identity is a constraint layer, never the sole credential.
- **A Tailnet Requirement does not protect itself unless `requirement-protection` is enforced.** With the control `off` or in `report` (the default), revoking or editing a Requirement needs `policy.manage` and nothing more: no Tailnet Context and no fresh passkey. A stolen credential that carries `policy.manage`, such as an Organization Admin's CLI sign-in, can remove the Requirement from off the tailnet and then retrieve what it constrained. Each change is audited (`requirement.updated`, `requirement.revoked`), so it is visible afterwards, not prevented. Under `enforce` such a change also needs the person's trusted passkey (section 4). What it still does not stop: someone who holds both the sign-in and one of the person's trusted passkeys (an approval is the requester's own, not a second person's); changes to Grants, roles and memberships, which reach the same values by other paths unless the organization also enforces `admin-step-up`; and the host operator's reset, which turns the control off from the host.
- **A machine credential may never expire unless `credential-lifetime` is enforced.** With the control `off` or in `report` (the default), a service credential issued without a lifetime lasts until it is revoked, and a lifetime of up to ten years is accepted. Under `enforce` new machine credentials get the organization's default lifetime and none lasts longer than its maximum (section 4). What it still does not do: change credentials issued before it was enforced (the credential review lists those without expiry), revoke a stolen credential before it expires, or bound a use budget; and the host operator's reset turns it off.
- **Administrative changes need only an admin's sign-in unless `admin-step-up` is enforced.** With the control `off` or in `report` (the default), a stolen admin credential (a CLI sign-in or a dashboard session) can mint machine credentials, widen Grants, promote itself, redirect webhooks, replace integration credentials, delete projects and export Secrets, each audited, none prevented. Under `enforce` each of these 40 operations also needs the person's trusted passkey (section 4). What it still does not stop: someone who holds both the sign-in and one of the person's trusted passkeys (an approval is the requester's own, not a second person's); the operations outside its list (value writes and rotations, Sync Targets under ADR-0031's own gate, Capabilities, member invitations, retiring and renaming machines, revoking credentials); value reads, `varlatch run`, sync, Capability exercise, OIDC exchange and a broker's agent-run credentials, so whoever holds `secret.reveal` can still read what an export would contain by those paths; what GitHub did before the approval was asked for (an App created by its manifest stays on GitHub); automation that makes these changes with a machine credential, which stops; and the host operator's reset (`admin security reset --control admin-step-up`), which turns it off from the host and closes the open approvals of all 40 operations. A person without a trusted passkey cannot approve and gets one back through `admin reenroll`.
- **The host operator can turn security controls off.** `admin security reset` runs on the host, needs nobody's passkey, and sets an organization's controls back to off (audited as `security_control.reset`). It is the way back when nobody can approve, and it means whoever controls the host or the deployment, including through deployment credentials that Varlatch itself serves, bypasses every control.
- **`passkey-verification` trusts the authenticator's own report, and only from the next request.** Whether a passkey verified the person is what the authenticator signed; Varlatch cannot tell a PIN from a skipped one beyond that flag. Sign-in still asks for user verification as `preferred`, so an authenticator without a PIN or biometric set up signs in unverified and is refused in an organization that enforces the control. A credential stolen after a verified sign-in is still accepted: the evidence describes the ceremony, not who holds the credential now. A request already past its decision point (a write's transaction, a retrieval's snapshot) finishes under the mode it read. What only decryption or an outside call can reveal (a value reference that cannot be expanded, a platform rejecting a credential) is never told to a refused request, since a refused request never decrypts or calls out. A person whose passkeys cannot verify them, admins included, gets back in only through the host operator's reset (`admin security reset --control passkey-verification`) or a trusted passkey enrolled with `admin reenroll`; turning the control down otherwise needs a step-up approval, which needs a passkey that verifies them. Turning it on from a sign-in it would refuse is refused, so its author cannot lock themselves out by accident; other admins can be, and report mode shows who first.
- **The incident freeze stops new requests, not what already ran.** The host operator can lift it from the host with `admin unfreeze`, with no passkey (audited as `organization.unfrozen` with no actor); `admin security reset` does not lift it. Processes that already hold values keep them, effects already sent stay sent, and credentials are not revoked. A stolen admin credential can freeze an organization, a denial of service it could already cause by revoking grants, but cannot lift it. Restoring a backup taken before a freeze lifts it. If the deploy or rollback credentials of an installation are served by Varlatch, freezing their organization stops deploys and rollbacks, Varlatch's own included: keep a break-glass credential outside Varlatch.
- **A signed-in session can add a passkey.** Adding a passkey from the dashboard needs a session, not a fresh assertion with an existing passkey, so a stolen session can add a passkey of its own and sign in with it later. Such a passkey is recorded as unconfirmed until the person confirms it with a trusted passkey, with user verification; passkeys enrolled through a setup or recovery link, and those that existed before the upgrade that introduced this record, are trusted. Only step-up approvals refuse on that basis: an unconfirmed passkey cannot approve one. Sign-in and device sign-in approval accept any passkey of the person; removing a trusted passkey needs a step-up approval while one of the person's organizations enforces a control, and otherwise accepts the session alone. Each session records whether the authenticator verified the user and which passkey signed in, which `passkey-verification` uses: such a sign-in is accepted in an organization that enforces it only once its passkey is confirmed.
- **Installing the CLI from the installation trusts the installation.** With `serve_cli = on` (off by default), the installation serves `/install.sh`, `/install.ps1` and the CLI file without a sign-in. Whoever controls the installation's host or its address can then run code on the machine of anyone who installs from it, beyond the values a compromise of the installation already exposes. The SHA-256 each script carries comes from the same server, so it only catches a damaged download. The scripts take the address from `public_url`, never from the request, and download only over https or loopback http; they follow no redirect, never use `sudo`, and replace an existing copy only after an answer in a terminal. The verified route, the GitHub release with its signature, stays documented beside it.
- **Memory cannot be reliably zeroized.** `varlatchd` clears the key material it read into buffers of its own and forbids core dumps and ptrace by other processes of its user, but Go's garbage collector copies and frees without erasing: no precise-erasure guarantee holds for plaintext or key material that has passed through the process.
- **Environment injection is disclosure.** Anything `varlatch run` places in a child's environment is fully readable by that process and everything it spawns. Varlatch cannot control what an arbitrary process does with plaintext it was handed.
- **Strict startup is a startup check, not a confidentiality control.** It validates what the command receives when it starts; values the command reads later, or changes itself, are outside it.
- **The Typed Accessor is a correctness check, not a confidentiality control.** A process can read everything in its environment, and the accessor's object is inspectable: logging it prints Secrets, as logging `process.env` would. Without a run context it cannot tell a withheld item from one that is not stored. Generated modules carry Contract metadata, defaults and examples included, so neither may hold a secret.
- **The agent-safe preflight does not establish the Agent's reference resolvability.** A matching state digest shows the same configuration, not the same permissions. Every exercise evaluates the Agent's authorization and resolves every reference or denies, and a later exercise may use a version the preflight never checked.
- **`varlatch run` cannot stop a process from leaking what it was given.** It is a plain injector. Output redaction (`--redact`, opt-in) is a guard against accidents, not a control: it masks only complete matches of the delivered Secrets, in the stated forms, in the command's stdout and stderr. Output that ends with part of a Secret, values under 8 bytes, hex or other transformed values, values split by other text, files the command writes, sockets, and `/dev/tty` are not covered, and terminal output is not redacted at all. It protects where output is written, not the command's own view, so it is not an agent protection. Agent-safe mode (§6) is the protection for untrusted processes.
- **Secret scanning is a guardrail, not data-loss prevention.** `varlatch scan` finds only complete occurrences of one environment's current and retiring Secret versions, in the stated forms. It does not find values under 8 bytes, hex or other transformed values, compressed content (archives and Git's packed objects included), a value with changed line endings, partial or split values, older versions, or other environments' Secrets. `--staged` checks what the next commit records, not Git history, and file names are not checked. A scan is a disclosure: it needs `secret.reveal`, so an identity without it, an Agent by default, cannot scan.
- **Authorization is effective at the snapshot boundary.** A retrieval is authorized by the Grants, Roles, Groups, Requirements, and Capability state in its database snapshot, and by nothing later. A revocation that commits after a request's snapshot began does not affect that request: it may still complete and return what the snapshot authorized. The next request sees the revocation. The window is one request, with no network call inside it. The audit event records the decision the snapshot produced, so it can follow the revocation's own event in audit order.
- **An audit event's client is what the caller says.** Events a request records for its own identity name the credential that authenticated it, which varlatchd verified, and a client summarized from the request's User-Agent (`Firefox on Linux`, `varlatch CLI 0.16.0 on Linux, assisted`), which it did not. Anyone holding a credential can send any User-Agent, so the client tells you which tool the credential holder used, the dashboard, the CLI, a coding agent in assisted mode, or the MCP server, not proof of it, and no authorization depends on it. A label holds only fixed words and a release version, never free text from the header.
- **Denial-of-service and side channels** (timing, traffic analysis) are out of scope for the MVP model.
- **Outbound sync is a deliberate egress class.** With a Sync Target configured, `varlatchd` initiates TLS connections carrying plaintext Values to allowlisted third-party APIs, authenticated by stored Platform Credentials. The mitigations (the closed adapter allowlist, KEK-wrapped org-level credentials scoped as narrowly as each platform honestly allows, audit-before-disclosure, the write-time disclosure gate, and the installation switch, `sync = off`) bound the egress; they are not a claim that it is riskless. Sync delivery is a server-side convergence loop, not a caller's retrieval: it decrypts values to detect what changed, and audits twice: before it decrypts (`sync.values_decrypted`, naming exact versions, even when nothing is pushed) and before any value leaves the process (`sync.push_attempted`). A stored Platform Credential can confer authority beyond reading Varlatch's secrets. Access checks, run before a credential is saved or a Target created, add read-only requests and no new destinations: no Value leaves, a stored credential goes only to its Connection's base identity, the reply is reduced to Varlatch's own verdict, and every check is audited. Choosing a Connection's host is a trust decision about where the Organization's Values go, never about the host's network: every request varlatchd makes for an Organization goes through the outbound policy described below. Destination listings, for the dashboard's pickers, follow the same rules and show that holder the names of the repositories or applications a credential can see; they could already attach the Connection to any of them, so the names disclose less than that authority. Listings keep only names and addresses, and are audited with a count.
- **The outbound policy's limits.** A hostname entry in `outbound_allow` trusts whoever controls that name's DNS records; an allowed destination is open to every Organization on the installation; the host's own public addresses stay reachable, as they are from the internet. Saving a refused destination tells the caller that the name exists in the host's DNS and its address class, never the address: less than the reachability answer earlier releases gave. `varlatch sync push` and the Broker run with the network access of the person's own machine and are outside the policy.
- **A GitHub App's key confers the App's whole authority.** Varlatch narrows every token it mints to one use, but the stored private key can mint any token the App's installations allow: for an App Varlatch registered, Secrets and Environments write and Metadata read on the installed repositories; for an imported App, whatever it holds (the import records extra permissions in the audit log). A `varlatchd` compromise with the Organization KEK reaches that key. Removing the App from Varlatch deletes the key there and nothing on GitHub: a key copied before removal stays valid until it is deleted on GitHub, and the App until its owner deletes it. Registration runs through the person's browser: the dashboard posts GitHub's form (its Content-Security-Policy allows forms to `https://github.com`), and GitHub sends a one-time code back to the dashboard, which the same actor completes with their own session; the key arrives from `api.github.com` over TLS in the code exchange.
- **The platform-facing copy is outside Varlatch's authority.** Once pushed, a Value's protection is the destination platform's: revocation and crypto-shredding do not extend there, an abandoned destination (after a destination change or Target revocation) is not cleaned up, and Varlatch never claims a pushed value was *adopted* by running workloads. Rotation completion stays a human decision informed by per-target sync status.
- **Deletion covers the live database, not its copies.** When a deletion completes, the current rows hold no envelope of the deleted values and no usable wrapped Organization KEK. SQLite does not overwrite the space it frees, so the file and its write-ahead log may hold deleted ciphertext and the destroyed key's wrapped form until the space is used again, as may the disk and its snapshots (the Root KEK is still needed to read any of it); a process may still hold keys or values in memory for requests already authorized, and a request in flight at finalization may still complete. Backups taken before the deletion completed hold the data until their retention removes them (a bucket with Object Lock keeps them for its whole term), and restoring one restores the whole installation, deleted data included. Values pushed to platforms, and copies people revealed, downloaded or exported, are not reached: rotate them at their provider. Removing a GitHub App's registration does not uninstall or delete the App on GitHub, revoke copies of its key, or revoke installation tokens already issued.

## 6. Agent safety: the credential broker (SHIPPED)

`varlatch run --agent-safe` spawns the untrusted Agent with opaque per-run
placeholders instead of Secrets and **no reusable Varlatch credential**
(the explicit `--agent-metadata` mode substitutes exactly one:
a ≤1h, revocable, HTTP-layer-read-only agent-run bearer whose authority is
still the Agent's Grants, so sensitive plaintext stays unreachable); a
trusted local Broker substitutes real material only in requests it
originates itself over verified TLS to Capability-allowlisted destinations;
`varlatchd` remains the `secret.use` authorization/Capability/audit
authority, re-evaluated on every exercise. Its guarantees are in the §4
table with their test mappings. The governing invariant:

> `secret.use` authorizes mediated use of secret material for an explicitly
> constrained destination. It does not imply `secret.reveal`.

And the honest limits, stated with the same discipline:

- **Same-user process escape is outside the boundary.** A process running as
  the same OS user may inspect the parent/Broker's memory, credential file,
  environment, or sockets. The Broker is not an OS sandbox.
- **Mediation, not a network sandbox.** Non-allowlisted traffic passes
  through unchanged by default (placeholders intact, useless);
  `--agent-network=strict` blocks it. An agent can still make arbitrary
  outbound requests unless separately sandboxed, and a `NO_PROXY` or
  `no_proxy` exemption inherited from the operator's shell sends matching
  requests around the Broker even in strict mode (the run adds only the
  Broker's own address to each spelling, and removes an inherited entry
  that would exempt every host).
- **Opaque CONNECT tunnels cannot carry substitution** without MITM, which
  Varlatch deliberately does not do (no local CA). Clients must send
  inspectable absolute-URI HTTP requests to the Broker; CONNECT to a
  secret-using destination is refused with a precise diagnostic. This is
  narrower than generic `HTTPS_PROXY` compatibility.
- **No response guarantee.** Varlatch prevents direct delivery of stored
  Secret plaintext to the Agent during credential injection. It does not
  guarantee that an authorized destination will never return secret-derived
  or plaintext data to the Agent. Response scrubbing is defense in depth:
  it replaces complete values exercised for the same request, in the forms
  listed in §4, and misses values under 8 bytes, hex, arbitrary `\uXXXX`,
  other character sets, compression inside a body, values split across
  fields, reflections in responses to other requests, and anything derived
  from a secret. When two Secrets share a region, only one Placeholder
  shows. A trailing prefix at a clean end is released unchanged, and output
  stalls while a possible match is pending.
- **Destination granularity is host+port**, not path or method.
- **Substitution targets bound where a Secret goes, not what it does.** A
  Placeholder is substituted only at the targets recorded on the
  Capability, but a correctly placed credential can still call any endpoint
  and method the destination permits, and a destination that logs or echoes
  the target header, or logs URLs with a query target, sees the value. Only
  the local Broker sees outbound requests, so varlatchd records what was
  authorized but cannot verify where a value was placed. Keep allowlists
  narrow and upstream credentials narrowly scoped.
- **Body targets are JSON and form bodies** of at most 2 MiB; the Broker
  cannot repair application signatures computed over placeholder-bearing
  payloads, the body, or its length.
- **A stray Placeholder is forwarded inert.** A Placeholder outside a
  targeted surface is sent unchanged and reported, not blocked.
- **The Agent inherits the rest of the operator's environment.** Stored
  Secrets and Contract Secrets are removed from it, but a secret Varlatch
  does not know about (not stored, not in the Contract) still reaches the
  Agent. Start agent-safe runs from a clean environment.
- **Plain `varlatch run` (without `--agent-safe`) still injects plaintext**
  into the child environment (§5); agent safety is opt-in per run.

A setup where an orchestrator issues Capabilities for brokers on other
machines (`capability.issue`, exercise-only OIDC bindings; the Go server)
limits each party, and no further than this:

- **A compromised broker machine** can exercise every live Capability it was
  given the secret of (with `runIdClaim`, of its run), at any recorded
  placement, for a destination it reports itself, and keep the values. It
  can use up a single-use Capability. It cannot list, read, issue, revoke or
  sign in as anything else with its credential, which lasts an hour at most;
  revoking the Capability, the credential or the broker stops it at its next
  request.
- **A compromised orchestrator** can issue, in the Environments of its Grant,
  Capabilities naming any item, any Agent of the Organization and any live
  broker, and hand their secrets out. It cannot exercise one itself. What
  they reach is bounded by the Agents' `secret.use` Grants: an Agent of its
  own for what the orchestrator schedules keeps that small. Removing its
  Grant, or retiring it, refuses every Capability it issued from the next
  exercise on. On an earlier server without delegation checks (after a
  rollback or reverse migration), delegated Capabilities fail closed and
  cannot be exercised at all.
- **An orchestrator that also signs the brokers' OIDC tokens is both at
  once**: it can exchange a token for any broker whose binding trusts its
  issuer, and exercise what it issues. Keep the issuer's signing key out of
  reach of the credential that holds `capability.issue`, or the limit is the
  Agents' Grants alone.
- **A replayed token** exchanges nothing under a binding with
  `singleExchange`, for as long as the token is valid. Whoever exchanges it
  first gets the credential: a thief that wins leaves the rightful holder
  refused (`token-already-exchanged` in the audit log). Restoring a backup
  restores what it knew of exchanged tokens: those exchanged after it, and
  still valid, can be exchanged once more. Bindings without the limit accept
  a token until it expires, as before. An identity's live bindings for one
  issuer are either all limited or all unlimited, so a rollback to an earlier
  server does not find an unlimited binding to exchange a limited one's tokens
  by. That server knows no limits and can add one: the tokens of that issuer
  then exchange as the identity there without limits, and not at all here
  (`mixed-bindings` in the audit log) until the bindings of one kind are
  revoked.
- **A guessed Capability ID** is told `Capability not found`, as another
  broker's, another run's or a wrong secret's is; the secret is 32 random
  bytes. Each attempt is in the audit log.
- **A granted exercise of a single-use Capability uses it up** even when the
  broker never receives the answer. A refused exercise, or one that delivers
  no item (none of the placed items has a value), does not.

## 7. Reviewing a claim

The rule this document lives by: **a strong security claim must map to an
automated test, an integration/E2E check, or a deployment invariant, or
explicitly say that the property cannot be enforced (usually: against the
Infrastructure Operator) and why.** If you find a claim here without one of
those, that is a documentation bug; file it as such.

## Bounds

Every write goes through one writer, which gives each audit event its position in commit order. Delivery to a webhook is at least once: a crash after a remote receiver accepts a batch but before the cursor is stored can replay it. Consumers must deduplicate event IDs.

On every listener, a request to the API with a body is capped at 1 MiB; the body of a GET, HEAD or TRACE request is discarded unread and not measured. A bounded process-local limiter permits 600 API requests per minute per client, excluding health checks: the connection's own address, the address `X-Forwarded-For` gives when the connection is a `trusted_proxies` entry (an address a caller writes into the header is not used), and on the tailnet listeners the recognized device. This is a basic abuse bound, not a distributed denial-of-service guarantee. Reference expansion is capped at 1 MiB, 10,000 substitutions, and eight reference levels.

Human recovery codes and a rotation of the Root KEK remain planned.
